# ADR-003: 客户端通信使用 gRPC

**日期**：2026-02-15
**状态**：已决定

## 背景

客户端（Native App）与服务端需要通信协议。需要支持普通请求-响应和流式回复。

## 决策

使用 gRPC (基于 HTTP/2 + Protocol Buffers) 作为主要通信协议。Rust 端使用 tonic 框架。

## 考虑过的替代方案

- **REST + SSE**：最简单，但协议不统一（REST 处理请求，SSE 处理流式，未来双向还得加 WebSocket，三套东西）。
- **WebSocket**：双向实时，但长连接不稳定，断线重连和心跳维护成本高。
- **gRPC 上面再封装传输抽象层**：讨论后否决。不同协议的语义差异太大（连接模型、错误处理、流式能力），抽象会退化为最大公约数，丢失 gRPC 的优势。

## 设计原则

**不抽象传输层，抽象业务层。** 业务逻辑放在 Application Service 层（协议无关），gRPC handler 只是薄适配器。未来如需 REST 接口（如 Web 端），加一个 REST handler 调同样的 Application Service。

```
┌────────────────────────────────┐
│ gRPC Service / REST Handler    │  ← 薄协议适配层
├────────────────────────────────┤
│ Application Service            │  ← 业务逻辑（协议无关）
├────────────────────────────────┤
│ Domain Layer                   │  ← 领域模型
└────────────────────────────────┘
```

## 后果

- ✅ 一套协议覆盖：请求-响应、服务端流式、双向流式
- ✅ .proto 文件即 API 文档，多端代码自动生成
- ✅ 二进制序列化性能好
- ✅ Rust (tonic)、Kotlin、Swift 都有成熟实现
- ⚠️ 学习成本（protobuf 语法、gRPC 概念）
- ⚠️ Web 端需要 gRPC-Web 代理（未来再处理）
- ⚠️ 调试不如 JSON 直观（需要工具）
