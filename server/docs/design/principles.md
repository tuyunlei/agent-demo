# 架构设计原则与品味约束

本文档是架构设计的最高级约束。所有设计决策、sub-agent 任务、review 都必须符合这些原则。

---

## 一、架构哲学

### 依赖方向：由外向内

采用 **Hexagonal Architecture（六边形架构 / Ports & Adapters）** 的核心思想：

```
外层（适配器）→ 依赖 → 内层（核心领域）
     ↑                    ↑
  可替换               不可替换
  (gRPC, PG, LLM)    (Agent, Session, Memory)
```

- **核心领域层**：纯业务逻辑，不依赖任何外部框架或基础设施。它定义接口（Rust trait / Port），不关心谁来实现
- **应用服务层**：编排业务流程，调用领域层的接口
- **适配器层**：实现核心定义的接口（gRPC handler、PG 存储、LLM 客户端等）

**依赖方向只能由外向内，绝不能反转。** 核心层永远不 import 适配器层的东西。

### 为什么选六边形而非三层架构？

传统三层架构（Controller → Service → Repository）的依赖方向是自上而下，Service 直接依赖 Repository 的具体实现。六边形架构通过 **依赖反转（DIP）**，让核心层定义接口，适配器层去实现，使得替换数据库、替换协议、替换 LLM 都不需要改核心逻辑。

对我们的项目来说，这一点至关重要——LLM provider 会换、通信协议可能加 REST、存储方案会演进，核心的 Agent 逻辑不应该因此改动。

## 二、设计原则（必须遵守）

### 2.1 关注点分离（Separation of Concerns）

每个模块只做一件事。不把传输逻辑混入业务逻辑，不把存储细节泄漏到领域模型。

**检查方法**：如果换掉 gRPC 改成 REST，需要改的文件是否只在适配器层？如果换掉 PostgreSQL 改成 SQLite，需要改的文件是否只在存储适配器？如果答案是"不是"，说明关注点分离不够。

### 2.2 依赖反转（Dependency Inversion）

高层模块不依赖低层模块，二者都依赖抽象。在 Rust 中，这意味着核心层定义 trait，适配器层 impl trait。

### 2.3 接口隔离（Interface Segregation）

不要设计"万能接口"。每个 trait 应该小而专注。消费者只依赖它需要的方法，不被迫实现一堆用不到的东西。

### 2.4 YAGNI + 预留扩展点的平衡

**不实现不需要的东西，但在需要扩展的地方留好接口。**

- ❌ "未来可能需要消息队列，先把 Kafka 集成进来" → 过度设计
- ❌ "LLM 调用直接硬编码 OpenAI SDK" → 没留扩展点
- ✅ "定义 LlmProvider trait，目前只实现 OpenAI，但换 provider 只需加一个实现" → 正确的平衡

**判断标准**：如果扩展只需要"加一个新的 trait 实现"而不需要"改已有代码"，说明扩展点留对了。

### 2.5 显式优于隐式

- 配置显式传递，不靠全局变量或环境变量魔法
- 错误显式处理（Rust 的 Result<T, E>），不吞错误、不 panic
- 依赖显式注入，不靠运行时反射或隐式单例

### 2.6 命名即文档

好的命名应该让人不读注释就知道这个东西是干什么的。如果需要注释才能解释一个函数的用途，说明命名或抽象有问题。

### 2.7 模块化结构：分层骨架 + 模块内树形拆分

系统级骨架保持三层：

```
Infrastructure Layer（gRPC、PostgreSQL、LLM 客户端）
       ↓ 依赖
Application Layer（Use Cases，如 SendMessageUseCase）
       ↓ 依赖
Domain Layer（Agent、Session、Memory 等核心业务实体）
```

依赖方向只能由外向内。这个分层是系统的稳定骨架，不因具体功能变化而改变。

当某个模块复杂度上升时，必须在模块内部继续树形拆分（通常 3-4 层），而不是把复杂度堆在一个大模块里。以 Application Layer 中的 Agent Runtime 为例：

```
Agent Runtime
├── RequestDispatcher   接收请求，路由给正确的 handler
├── ContextAssembler    组装 LLM context（历史 + 人格 + 记忆）
├── ExecutionLoop       驱动 LLM 调用 + 工具执行的主循环
│   ├── LlmCaller       封装 LLM 流式调用
│   └── ToolCoordinator 协调工具请求/结果的收发
└── PostProcessor       处理完成后的收尾（存储、事件发送）
```

模块化不是为了形式，而是为了可理解性与可验证性：

- **认知载荷约束**：每个模块都应控制在一次 session 能完整理解其职责、输入输出与边界
- **独立可测**：每个模块都必须可以被单独测试；其依赖的 Port 必须可被 mock/stub 替代

### 2.8 Walking Skeleton 原则

架构设计必须支持**最小路径先跑通**，而不是等所有模块完整实现后才能运行。

- 每个 Port 都必须允许 Stub 实现，且不影响其他模块联调
- 先打通端到端最短闭环，再逐步把 Stub 替换为真实实现

当前系统的最小路径可以是：

`SendMessage → Agent Runtime（最简版）→ LLM → 返回`

设计评审时必须问一个问题：**如果这个模块暂时缺失，能否用 Stub 让整个流程先跑起来？**

如果答案是否定的，说明模块边界或依赖设计仍然过紧。

## 三、品味标准（追求卓越）

### 3.1 简洁而非简单

简单是"少做事"，简洁是"用最少的概念表达完整的意图"。追求简洁，不追求简单。

- ❌ 简单：所有逻辑写在一个文件里（少但乱）
- ❌ 复杂：10 层抽象只为了一个功能（多且没必要）
- ✅ 简洁：恰到好处的分层，每层职责清晰

### 3.2 一致性

整个系统的设计风格应该统一：
- 错误处理方式统一
- 命名约定统一
- 模块组织方式统一
- 接口设计风格统一

不一致比"不够好"更糟糕。

### 3.3 可演进性

好的架构不是一步到位的，而是**支持低成本演进**的。

- 每个设计决策都应该问：**如果这个决策错了，改正的成本有多大？**
- 高改正成本的决策要慎重（数据模型、核心抽象）
- 低改正成本的决策可以快速决定（具体工具的实现细节）

### 3.4 不造新概念

尽量使用业界已有的、被验证过的概念和术语。不发明新的名词来描述已有的东西。

### 3.5 避免五大反模式

1. **Big Ball of Mud**：没有清晰架构，代码纠缠。→ 用六边形分层避免
2. **Golden Hammer**：什么都用同一个技术。→ 每个问题选最合适的工具
3. **Stovepipe**：模块之间完全隔绝不通信。→ 通过定义良好的接口交互
4. **Magic Box**：某个模块没人理解。→ 文档 + 接口清晰
5. **Reinventing the Wheel**：有现成方案还自己写。→ 优先用成熟库

## 四、Rust 特有的架构考量

### 4.1 Trait 是架构的骨架

Rust 的 trait 天然对应六边形架构的 Port。用 trait 定义所有关键抽象：
- `LlmProvider`：LLM 调用接口
- `MessageStore`：消息存储接口
- `ToolExecutor`：工具执行接口
- `Channel`：消息入口接口

### 4.2 错误处理分层

- 领域层：定义领域错误类型（`DomainError`）
- 应用层：定义应用错误类型（`AppError`），封装领域错误
- 适配器层：将外部错误转换为应用错误

不要让 `sqlx::Error` 或 `tonic::Status` 出现在核心层。

### 4.3 异步但不滥用

不是所有东西都需要 async。纯计算逻辑用同步，只有 I/O 密集的操作用 async。

### 4.4 Async Trait 策略要尽早定

Rust 中 async 接口的建模策略（如基于 `dyn Trait` 的对象化方案，还是基于泛型参数的静态分发方案）必须在架构早期统一。

这不是局部实现细节，而是会影响所有 Port 定义、依赖注入方式与模块组合方式的全局决策。后期再切换，改动面通常横跨核心层与适配器层，代价很高。

### 4.5 所有权即设计

Rust 的所有权关系应当直接体现模块边界与职责划分。

- 边界清晰的模块，应有清晰的数据拥有者与生命周期责任
- 不要用共享状态把本该解耦的模块重新黏在一起

`Arc` 是解决并发与共享需求的工具，不是弥补架构边界不清的手段。

---

*这些原则不是教条。如果某个具体场景下违反原则能带来显著收益，应该记录为 ADR 并说明理由。*
