# 并发模型设计（Rust + Tokio）

> 适用范围：多用户托管式 AI Agent SaaS（MVP 单实例），六边形架构，后端 Rust + Tokio + gRPC + PostgreSQL。
>
> 目标：在 **Session 单写者一致性** 前提下，支持高并发请求、长连接流式输出、工具并行执行，并具备明确的超时、背压与故障恢复机制。

---

## 1. 并发模型总览

## 1.1 设计原则

- **Session 是最小并发一致性单元**：同一 session 同时仅允许一个“写流程”推进。
- **请求级异步、Session 内串行**：系统整体并发靠 Tokio task；同 session 内通过单写者约束串行化。
- **显式边界**：每层都声明并发边界（队列、信号量、连接池、超时、取消域）。
- **Domain 无异步细节**：并发、锁、背压、流控全部在 Application/Infrastructure。
- **MVP 可落地，后续可水平扩展**：先单实例稳定，再演进到多实例分布式锁与分片路由。

## 1.2 Tokio 运行时使用策略

- 使用 Tokio 多线程 runtime（I/O + 计时器 + task 调度）。
- **任务分层**：
  - **入口任务**：每个外部请求（gRPC）对应一个 request task。
  - **会话执行任务**：实际“写流程”在 session 执行上下文中运行（单写者）。
  - **子任务**：工具并行调用、流广播、异步持久化等作为受控子任务。
- **阻塞隔离**：潜在阻塞操作（CPU 重、阻塞库）必须显式隔离（专用线程池或 blocking 通道），避免污染 async worker。
- **结构化并发**：子任务属于父请求取消域，父任务结束/超时/取消时统一传播。

## 1.3 任务粒度

- **是：一个用户请求 = 一个入口 Tokio task。**
- 但不是“一个 task 完成所有并发控制”。入口 task 只负责：
  1) 鉴权/限流/幂等校验；
  2) 进入 session 调度器（获取执行权或排队/拒绝）；
  3) 绑定流输出与取消上下文。
- 真正的业务推进在 session 执行上下文中串行处理，确保 message 顺序与状态一致。

## 1.4 与六边形架构关系

- **Domain 层**：纯业务规则（状态机、消息语义、工具结果解释），不感知 Tokio/task/channel。
- **Application 层**：
  - 编排请求流水线；
  - 管理 session 执行器、超时、取消、背压策略；
  - 定义端口（LLM、Tool、Repo、EventBus）。
- **Infrastructure 层**：
  - Tokio runtime 集成、gRPC 适配、PostgreSQL 连接池、外部工具调用、流式传输实现。

## 2. Session 级并发控制

## 2.1 单写者模型实现策略（MVP 推荐）

采用 **双层保障**：

1. **进程内 Session Actor/Channel（主路径）**
   - 每个活跃 session 对应一个轻量执行器（mailbox + 单消费者）。
   - 同一 session 的写请求进入同一 mailbox，天然串行。
   - 优点：低延迟、可做队列策略、便于流式事件挂接。

2. **数据库 advisory lock（兜底一致性）**
   - 在关键写事务前获取 session 级 advisory lock（短持有）。
   - 防止进程异常、未来多实例、或逻辑绕过时出现并发写。
   - 锁仅覆盖“状态提交临界区”，避免长时间占用。

> 说明：仅依赖 DB 锁会导致请求体验差（阻塞不可见）；仅依赖进程内 actor 在未来多实例有风险。双层兼顾 MVP 与演进。

## 2.2 请求排队 vs 拒绝策略

按请求类型区分：

- **写请求（用户新消息）**：允许短队列。
  - 每 session 队列上限：`N=2`（MVP 建议，含执行中外最多 3 个）。
  - 超过上限直接拒绝（`SessionBusy`），提示稍后重试。
- **控制请求（cancel/retry）**：高优先级插队（不经普通队列尾部）。
- **读请求（历史查询）**：不进入单写者队列，但受全局读资源限额。

这样可避免单 session 被无限堆积拖垮系统。

## 2.3 长时间占用 session 的超时释放

显式定义三层超时：

- **总 wall clock**：`60s`（已给定，硬上限）。
- **阶段超时**：例如模型首 token 超时、工具单次超时、DB 操作超时（见后文）。
- **空闲心跳超时**：流式阶段若长期无进展（如 `10s` 无 token/事件）触发中断。

释放规则：

1. 任一硬超时触发取消；
2. 请求状态写入终态（timeout/cancelled/partial）；
3. 释放 session 执行权与队列占位；
4. 向订阅端发送最终事件并关闭流。

## 3. 请求处理流水线

## 3.1 端到端异步流程（用户消息 → 响应完成）

1. **Ingress**（gRPC 接入）
   - 鉴权、租户/用户限流、request_id 幂等检查。
2. **Session Admission**
   - 路由到 session 执行器；队列判定（入队/拒绝）。
3. **上下文装载（可并行）**
   - 读取 session 元数据、近期消息、工具配置等（并行 I/O）。
4. **推理循环执行（串行为主）**
   - 按 Agent Runtime 已定义流程推进（最多 8 轮工具循环）。
5. **流式事件输出（并行旁路）**
   - 生成 ChatEvent 并推送到事件总线/订阅者。
6. **状态提交（串行临界区）**
   - 持久化消息、状态版本、审计字段（短事务）。
7. **完成/失败收尾**
   - 发送终态事件，释放资源，记录指标。

## 3.2 并行 vs 串行边界

- **可并行**：
  - 上下文多源读取；
  - 同轮 parallel_safe 工具调用（≤4）；
  - 事件广播给多个订阅端。
- **必须串行**：
  - 同 session 的状态推进；
  - message 顺序落库；
  - session 终态提交。

## 3.3 背压机制

三层背压：

1. **入口背压**：全局并发信号量 + 每用户并发上限。
2. **session 背压**：每 session 有界队列（上限 2），超限拒绝。
3. **流背压**：
   - ChatEvent 通道使用有界缓冲；
   - 慢消费者触发降级（丢弃非关键增量事件，只保留关键事件：start/chunk-summary/final/error）；
   - 极慢客户端可断流但不影响主执行。

## 4. 流式输出的并发管理

## 4.1 全链路模型

`LLM token stream -> ChatEvent 规范化 -> Session Event Bus -> gRPC Stream(s)`

- LLM Gateway 输出 token 增量。
- Application 层将其转换为统一 ChatEvent（带 session_id/request_id/seq）。
- Session Event Bus 负责广播到一个或多个 gRPC 订阅流。
- gRPC 层仅做传输适配，不持有业务状态。

## 4.2 生命周期管理

### 正常结束
- LLM 正常 EOF；
- 发送 `ResponseCompleted`；
- 持久化终态；
- 关闭该 request 的事件分支。

### 异常中断（上游错误/超时）
- 立即发 `ResponseFailed`（含可观测错误码）；
- 执行取消传播（工具子任务、下游发送任务）；
- 落库失败终态并释放 session。

### 客户端断连
- 只关闭该客户端订阅分支；
- **默认不取消**服务端执行（面向“断线重连继续看结果”）；
- 若无任何订阅者且策略为节省资源，可在阈值时间后自动降级/取消（MVP 可先不启用）。

## 4.3 多端订阅同一流

- 一个 request 对应一个可复用事件源（按 request_id）。
- 多终端通过订阅注册获取同一事件序列。
- 事件带单调递增 `seq`，支持断线后按 `last_seq` 续传（MVP 可先支持“从最新点订阅”，续传做演进项）。

## 5. 工具并行执行

## 5.1 Tokio task 调度

- 同轮工具调用采用受控并发：`max_parallel_tools = 4`（已给定）。
- 每个工具调用是独立子任务，纳入父请求取消域。
- parallel_safe 才可并行；非 parallel_safe 强制串行。

## 5.2 超时控制

显式两层：

- **单工具超时**：建议 `8~15s`（按工具类别配置）。
- **请求总超时**：`60s wall clock`，优先级最高。

规则：若剩余 wall clock < 工具默认超时，则工具超时动态收敛到剩余预算。

## 5.3 取消传播与失败策略

- **默认策略：失败隔离 + 轮次可判定失败**
  - 某工具失败不立即取消同轮其他工具（避免损失已接近完成的结果）。
  - 本轮结束后由 Runtime 判定：继续下一步、重试、或整体失败。
- **硬失败条件触发全取消**：
  - 总超时触发；
  - session 被显式 cancel；
  - 关键不可恢复错误（如上下文损坏）。

此策略兼顾吞吐与可用性，避免“一错全停”过于激进。

## 6. 数据库连接管理

## 6.1 连接池配置策略（MVP）

以 PostgreSQL 单实例为前提：

- 连接池大小建议：`min=10, max=40`（按实例 CPU/内存与 p95 延迟调优）。
- 按职责预留：
  - 读写主路径池（请求处理）；
  - 后台任务/审计可共享但受独立并发闸门。
- 设置获取连接超时（如 `100~300ms`），超时即快速失败并上抛 `Overloaded`。

## 6.2 事务隔离级别

- 默认 `READ COMMITTED`（MVP 推荐）。
- 关键一致性靠：
  - session 单写者 + advisory lock；
  - 幂等键与唯一约束；
  - 显式版本号（必要处 optimistic check）。
- 仅在少量强一致场景使用更高隔离，避免全局吞吐下降。

## 6.3 避免长事务

- 禁止把 LLM 流式调用、工具调用包进事务。
- 采用“短事务分段提交”：
  1) 读取快照；
  2) 外部长耗时执行（无事务）；
  3) 最终短事务提交结果。
- 对 message 写入采用 append-only + 版本检查，减少锁竞争。

## 7. 资源限制与保护

## 7.1 全局并发限制

- 全局请求并发信号量（例：`200`，按机器规格调优）。
- 超限立即返回 `ServerBusy`，避免排队雪崩。
- 关键下游（LLM、DB、工具执行器）各自独立并发闸门，避免互相拖垮。

## 7.2 每用户并发限制

- 每用户活跃写请求上限（建议 `1~3`）。
- 同用户多 session 可并发，但总量受用户级配额控制。
- 与产品套餐绑定（Free/Pro 可不同配额）。

## 7.3 内存使用控制

- 上下文窗口按 token 预算裁剪（硬上限 + 回溯策略）。
- 流式缓冲采用有界 ring buffer，不无限累积 token。
- 大工具结果落对象存储/临时文件，仅在内存中保留摘要与引用。
- 每请求内存预算超阈时触发降级（截断历史/简化事件）。

## 7.4 优雅关闭（graceful shutdown）

- 接收停机信号后：
  1) 停止接收新请求；
  2) 给在途请求宽限期（如 `30s`）；
  3) 到期后取消剩余任务并写入终态；
  4) 刷新关键缓冲并关闭连接池。
- 通过健康检查状态切换（ready=false, live=true -> false）配合上游摘流量。

## 8. 错误处理与恢复

## 8.1 Tokio task panic 处理

- 所有关键 `spawn` task 必须被 `JoinHandle` 监管。
- 发生 panic：
  - 捕获并记录（带 session_id/request_id）；
  - 将请求标记为内部错误终态；
  - 触发会话执行器自恢复（重建 actor/mailbox 状态）。
- panic 不能静默吞掉，必须进入告警与指标。

## 8.2 部分失败（工具部分成功）

- 结果模型区分：`success | partial | failed`。
- 并行工具中已成功结果可保留用于后续推理；失败项带结构化错误返回。
- 最终响应允许“部分可用”并向用户透明提示。

## 8.3 状态不一致自愈

典型不一致：请求中断但 session 卡占用、事件流终止但状态未落库。

自愈机制：

1. **启动时恢复扫描**：扫描“进行中且超时未更新”的请求，标记为 aborted。
2. **租约/心跳字段**：session 执行占用写入 lease_expire_at，超时可回收。
3. **幂等重放**：同 request_id 重试时读取既有状态，避免重复写入。
4. **运维修复接口**：提供按 session/request 的安全解锁与重置操作（审计留痕）。

## 9. MVP 配置基线（建议初始值）

- 全局并发请求：`200`
- 每用户并发写请求：`2`
- 每 session 队列长度：`2`（超限拒绝）
- 工具并行上限：`4`（已定）
- 工具循环上限：`8`（已定）
- 请求总超时：`60s`（已定）
- 单工具超时：`10s`（类别可配）
- DB 连接池：`min 10 / max 40`
- graceful shutdown 宽限期：`30s`

> 以上为起步参数，需以压测结果和线上指标（p95/p99、错误率、队列长度、内存水位）闭环调优。

## 10. 演进方向（从 MVP 到多实例）

1. **单实例阶段（当前）**
   - 进程内 session actor + DB advisory lock 兜底。
2. **多实例阶段**
   - session 路由一致性（hash 分片或粘性路由）；
   - 分布式锁/租约统一化；
   - 事件总线外置（用于跨实例多端订阅）。
3. **高可靠阶段**
   - 请求日志化与可重放；
   - 更细粒度隔离舱（租户级资源池）；
   - 自动化自愈与限流策略动态调整。
