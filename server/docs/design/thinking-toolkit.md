# 思考框架工具箱

架构设计适用的思考框架，按用途分三层：问题定义 → 分析推理 → 方案表达。

---

## 一、问题定义层 — "我们到底在解决什么问题？"

### 第一性原理 (First Principles Thinking)
- **核心**：剥掉"别人怎么做的"，回到最基本的事实和需求，从零重建
- **用法**：不被 OpenClaw/ChatGPT 的现有做法框住，从用户根本需求出发
- **三步**：①识别并质疑假设 → ②还原到基本事实 → ③从基本事实重建方案

### JTBD (Jobs To Be Done)
- **核心**：用户不是在"买产品"，而是在"雇佣一个方案来完成某个 job"
- **用法**：定义产品边界——用户要的不是"一个 agent 平台"，而是某个具体的 job
- **关键问题**："用户在什么场景下，雇佣我们的产品来完成什么任务？"

### SCQA (Situation-Complication-Question-Answer)
- **核心**：用四段结构把问题讲清楚，确保所有人对齐
- **格式**：
  - Situation（现状）：当前世界是什么样的
  - Complication（矛盾）：出了什么问题、有什么不满足
  - Question（核心问题）：所以我们要回答什么
  - Answer（方案）：我们的回答是什么

### 5 Whys
- **核心**：对任何结论连问 5 层 why，挖到根因
- **用法**：质疑每个设计假设——"为什么要沙盒？""为什么要多租户？"

## 二、分析推理层 — "怎么拆解、怎么权衡？"

### MECE (Mutually Exclusive, Collectively Exhaustive)
- **核心**：不重不漏地拆分问题空间
- **用法**：拆解架构关注点时确保没遗漏

### 逆向思维 (Inversion)
- **核心**：不问"怎么成功"，而问"怎么会失败"，然后避免那些失败模式
- **用法**："这个系统怎样会挂？""用户怎样会流失？""什么会让运维成本爆炸？"

### Pre-mortem
- **核心**：假设项目已经失败了，回溯分析"它是怎么死的"
- **用法**：在动手前就识别致命风险

### 二阶思维 (Second-Order Thinking)
- **核心**：不止看一个决策的直接后果，还要想"然后呢？"
- **用法**：比如"选容器隔离"→ 冷启动慢 → 体验差 → 需预热 → 成本涨 → …
- **贯穿使用**：不是独立步骤，是思维习惯

### 约束优先 (Constraint-First)
- **核心**：先列硬约束（不可妥协），再在约束内找最优解
- **用法**：团队大小、预算、上线时间、安全底线——先定框，方案在框里画

### Trade-off Analysis
- **核心**：对关键决策明确列出两边的 pros/cons，不存在"最优解"，只有"在约束下最合适的"
- **用法**：容器 vs 进程隔离、SQL vs NoSQL、自建 vs 托管……

### Wardley Mapping
- **核心**：把价值链上的每个组件按演化阶段排列（Genesis → Custom → Product → Commodity）
- **用法**：判断哪些该自建（差异化竞争力）、哪些该用现成的（commodity）
- **关键洞察**：越靠近 commodity 的越不该自建，越靠近 genesis 的越可能是竞争壁垒

### 系统思维 (Systems Thinking)
- **核心**：关注反馈回路、涌现行为、非线性效应，不孤立看单个组件
- **贯穿使用**：改动一个点会牵连很多，需要看全局

### 概率思维 (Probabilistic Thinking)
- **核心**：不做二元判断，评估各种可能性的概率
- **贯穿使用**："用户量到 X 规模的概率？""这个风险发生的概率？"

## 三、方案表达层 — "怎么把想清楚的东西画出来、记下来？"

### C4 模型
- **核心**：4 层递进的架构视图
  - Level 1 Context：系统与外部世界的关系
  - Level 2 Container：系统内的大块（服务、数据库、消息队列等）
  - Level 3 Component：每个 Container 内部的模块
  - Level 4 Code：具体实现（通常不画）
- **用法**：从宏观到细节逐步深入

### DDD (Domain-Driven Design)
- **核心**：用业务领域的语言来建模
- **关键概念**：Bounded Context（限界上下文）、Aggregate、Entity、Value Object
- **用法**：定义系统的领域边界——"用户管理"、"Agent Runtime"、"工具沙盒"各是一个 bounded context

### Event Storming
- **核心**：用事件流来发现领域模型
- **步骤**：先列所有"发生了什么事件"，再倒推"谁触发的""影响了什么"
- **用法**：梳理核心流程——用户发消息 → 路由到 agent → agent 调工具 → 返回结果

### ADR (Architecture Decision Records)
- **核心**：每个关键决策记录 context、decision、alternatives、consequences
- **用法**：不忘"当初为什么这么选"
- **存放**：`decisions/` 目录，编号命名（001-xxx.md, 002-yyy.md）

### arc42
- **核心**：完整的架构文档模板（12 章节）
- **用法**：需要系统性输出文档时参考，早期不需要

## 推荐使用顺序

对我们当前阶段（早期讨论），推荐的最小组合：

1. **JTBD + 第一性原理** → 定义问题
2. **SCQA** → 对齐理解
3. **约束优先 + MECE** → 列约束，拆解设计空间
4. **逆向思维 / Pre-mortem** → 排雷
5. **Wardley Mapping** → 决定自建 vs 用现成的
6. **C4** → 画架构
7. **ADR** → 记录决策

二阶思维、概率思维、系统思维不是独立步骤，而是贯穿全程的思维习惯。
