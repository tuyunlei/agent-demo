# ADR-007: 事件流数据模型

**状态**: Accepted
**日期**: 2026-02-24

## 上下文

早期模型以消息快照为核心，能满足基础聊天存储，但随着工具循环、压缩、审计、回放与 prompt 优化需求增长，出现明显限制：

- 无法自然表达工具调用请求/结果等中间事实
- 会话压缩缺乏明确替代边界
- 难以对一次 turn 做完整回放和审计
- System Prompt 配置变更缺乏事件化表达
- prompt cache 友好策略（稳定前缀）难以落地

新架构需要一种能统一“写入事实”和“读出投影”的模型。

## 决策

将会话核心数据模型从“消息快照”迁移为“append-only 事件流”：

1. 事件流作为 source of truth；消息列表仅是投影。
2. 每个 session 内事件按 `sequence_number` 递增追加。
3. 事件类型覆盖消息、工具、系统、配置与压缩语义。
4. 压缩通过 `Summary + CompactionMarker` 表达，不改写历史。
5. 配置演进通过 `ConfigChange` 事件表达，支持稳定 system prompt 与 cache 复用。

## 理由

对比三种方案：

1. **消息快照模型**
   - 优点：简单、上手快
   - 缺点：中间事实弱、审计与回放能力差、压缩语义弱
2. **事件流模型（本决策）**
   - 优点：可审计、可回放、可扩展、与压缩和 prompt 策略天然兼容
   - 缺点：读模型复杂度更高，需要投影与裁剪
3. **混合模型（消息+事件双真相）**
   - 优点：迁移平滑
   - 缺点：双写一致性与语义冲突成本高，长期治理复杂

选择事件流，是因为其在中长期架构稳定性和可维护性上收益最高；混合仅可作为短期迁移手段，不作为目标真相模型。

## 后果

### 正面影响
- Turn 过程可追踪、可回放，排障成本下降。
- 压缩机制与上下文组装有统一语义。
- 对工具调用、多步骤编排、审计需求更友好。
- 为后续分析/观测/治理提供统一事实基础。

### 负面影响
- 读路径需要额外投影层与 token-aware 选择策略。
- 迁移期需要处理旧消息模型兼容。
- 团队需要从“状态更新思维”转向“事件追加思维”。
