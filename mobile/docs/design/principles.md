# 客户端架构原则与分层规范

> 适用范围：iOS / Android / HarmonyOS 客户端
>  
> 本文档定义客户端架构的基线约束，作为后续模块设计（M03-M06）与技术选型（M02）的上位规范。

---

## 1. 架构总览

客户端采用四层分层模型：

```
应用集成层 (App Integration)
        ↓
业务层 (Business)
        ↓
服务层 (Service)
        ↓
基础层 (Foundation)
```

**唯一依赖规则：依赖只能向下，不能反向。**

- 上层可依赖下层
- 下层不可感知上层
- 同层模块默认不直接耦合，优先通过接口协作

---

## 2. 四层定义、边界与依赖规则

| 层级 | 核心职责 | 典型内容 | 禁止事项 | 三端策略 |
|---|---|---|---|---|
| 应用集成层 | 组合根、启动编排、服务注册、Root 页面装配 | App 启动流程、DI 装配、路由入口 | 承载具体业务规则 | **平台特定** |
| 业务层 | 按业务域垂直切分模块，承载业务状态与交互规则 | 页面/流程逻辑、SARE、业务用例 | 直接操作底层 SDK 或跨层跳转依赖 | **接口+逻辑三端对齐，UI 平台特定** |
| 服务层 | 提供全局可复用能力，屏蔽外部系统细节 | 网络、存储、认证、推送、日志等服务接口与实现 | 反向依赖业务模块 | **接口三端对齐，实现可平台特定** |
| 基础层 | 通用组件与基础能力沉淀 | 通用工具、三方库封装、跨平台共享代码 | 引入业务语义 | **尽可能跨平台共享** |

### 2.1 依赖方向（强约束）

- 应用集成层 → 业务层 / 服务层 / 基础层
- 业务层 → 服务层 / 基础层
- 服务层 → 基础层
- 基础层 → 不依赖上层

若出现反向依赖，必须重构边界，不允许以临时绕过方式长期存在。

---

## 3. 业务层内部子层规范（按需选用）

业务模块内部可采用以下子层，目标是“清晰边界 + 最小必要分层”：

1. **接口层（可选）**
   - 仅在“被其他模块依赖”时拆出
   - 对外暴露稳定契约，隐藏内部实现

2. **实现层（必需）**
   - 承载核心业务逻辑与流程编排
   - 通过服务层接口完成外部能力调用

3. **UI 层（必需，且必须分离）**
   - 仅做状态绑定与事件分发
   - 不直接访问网络/存储

4. **Model 层（按需）**
   - 模块内部数据结构与状态模型
   - 跨模块共享模型应下沉到服务层/基础层

原则：**不是层越多越好，而是边界足够清晰且可测试。**

---

## 4. 六条架构原则（必须遵守）

### 4.1 严格分层 + 依赖只能向下
分层是可维护性的前提。任何跨层逆向依赖都会导致耦合扩散，必须禁止。

### 4.2 高度模块化，独立可测
每个模块都应可通过 mock 依赖进行单测与集成测试，避免“必须整仓联调”才能验证。

### 4.3 视图与业务逻辑解耦
视图层只消费状态、发送事件，不直接处理网络/存储/鉴权等副作用。

### 4.4 三端共享规范，平台实现分离
统一业务与数据契约，允许平台侧在 UI 与底层实现上各自优化，确保一致性与灵活性并存。

### 4.5 单向数据流
状态自上而下传递，事件自下而上回流；避免双向绑定导致状态失控。

### 4.6 网络不可靠是设计前提
默认网络随时可能失败或中断。所有关键流程必须有超时、重试、降级与恢复策略。

---

## 5. 页面级统一模式：SARE

每个页面/业务模块统一使用 **SARE（State + Action + Reducer + Effect）**：

- **State**：完整、不可变的 UI 状态
- **Action**：用户操作或系统事件
- **Reducer**：纯函数 `(State, Action) -> NewState`
- **Effect**：副作用（网络、存储、通知等），与 Reducer 显式隔离

### 5.1 最小闭环

`Action -> Reducer -> State -> UI` 形成主回路，`Effect` 负责与外部系统交互后再派发新 Action。

### 5.2 三端一致性要求

- Swift / Kotlin / ArkTS 实现可不同
- 状态语义、动作语义、Reducer 行为必须一致
- 同一业务在三端应满足同构行为，避免“同功能不同逻辑”

---

## 6. AI 时代强化原则

### 6.1 模块自描述
每个模块应具备：接口、类型、最小文档、测试样例。让 AI 与人都能快速理解边界与意图。

### 6.2 接口即规格书
接口定义必须精确（输入、输出、错误、约束）。接口越清晰，AI 生成代码越稳定。

### 6.3 模块粒度适配 Context Window
控制模块规模，确保单模块可在一次上下文中被完整理解与修改。

### 6.4 Boilerplate 可由 AI 承担
SARE 的模板化代码应标准化生成，把人类精力留给边界设计与关键决策。

## 7. 三端共享与平台特定划分策略

| 维度 | 共享策略 | 说明 |
|---|---|---|
| 业务规则 | 优先共享“语义与契约” | 流程、状态机、错误语义保持一致 |
| 页面状态模型 | 共享结构定义与字段语义 | 类型系统可因语言差异做等价映射 |
| UI 渲染 | 平台特定 | 各端遵循各自设计规范与组件体系 |
| 服务接口 | 三端统一 | 如网络/存储/认证接口契约统一 |
| 服务实现 | 可平台特定 | 适配各端系统能力与 SDK 差异 |
| 基础工具能力 | 尽量共享 | 通用算法、协议模型、工具库优先下沉共享 |

决策优先级：**先保证体验一致与可维护，再追求代码物理复用率。**

---

## 8. 与服务端架构原则的对照（互补关系）

服务端采用六边形（Ports & Adapters），核心思想是“内层定义接口，外层提供实现，依赖由外向内”。

客户端四层与其在设计哲学上互补一致：

1. **契约先行一致**：客户端业务/服务接口，对齐服务端 Port 思想
2. **实现可替换一致**：客户端平台实现、服务端适配器实现都可替换
3. **核心稳定一致**：客户端业务语义与服务端领域语义都应避免被外部技术细节污染

可形成端到端协作模型：

- 服务端稳定输出领域能力与接口契约
- 客户端在四层内完成状态管理、交互编排与平台适配
- 双方通过“清晰接口 + 单向依赖 + 可替换实现”实现长期演进

---

## 9. 执行与审查清单（用于设计评审）

- 是否严格满足四层边界与向下依赖？
- 模块是否可独立测试并可 mock 依赖？
- UI 是否完全不直接触达网络/存储？
- 是否采用 SARE 且副作用已隔离？
- 三端是否做到“规范共享、实现分离”？
- 网络失败场景是否被当作默认前提处理？
- AI 是否可仅凭接口与文档快速接手模块？
