## 必要上下文

### 四层分层（已确认）

```
应用集成层    组合根 + 启动 + 服务注册 + Root 页面         平台特定
业务层       按业务垂直切模块，子层按需：接口/实现/UI/Model  接口+逻辑三端对齐，UI 平台特定
服务层       网络 · 存储 · 认证 · 推送，全局通用服务        接口三端对齐，实现可能平台特定
基础层       通用组件 · 三方库封装 · 跨平台共享代码         尽可能跨平台共享
```

依赖方向：只能向下，不可反向。

### 6 条架构原则（已确认）

1. **严格分层 + 依赖只能向下**
2. **高度模块化，独立可测**：每个模块可以 mock 依赖单独测试
3. **视图与业务逻辑解耦**：视图只绑定状态，不直接碰网络/存储
4. **三端共享规范，平台实现分离**：业务逻辑层和数据层定义统一接口
5. **单向数据流**：状态从上往下，事件从下往上
6. **网络不可靠是设计前提**：设计时假设网络随时会断

### 页面级 SARE 模式（已确认）

每个业务模块/页面统一使用 State + Action + Reducer + Effect 模式：
- **State**：描述完整 UI 状态的不可变数据结构
- **Action**：用户操作或系统事件
- **Reducer**：纯函数，接收 (State, Action) → 新 State
- **Effect**：副作用（网络请求、存储操作等），被显式隔离

三端统一这个模式，各端用各自语言实现（Swift/Kotlin/ArkTS），但行为一致。

### AI 时代强化（已确认）

- **模块自描述**：接口 + 类型 + 文档 + 测试，AI 读了就能工作
- **接口即规格书**：接口定义越精确，AI 生成的实现越靠谱
- **模块粒度适配 context window**：每个模块小到 AI 能在一个 context window 里完全理解
- **Boilerplate 不再是负担**：SARE 模式的重复性代码由 AI 生成，传统时代的缺点不再适用

### 业务层子层说明

- **接口层**：只有被其他模块依赖时才需要拆出
- **实现层**：模块的核心业务逻辑
- **UI 层**：始终分离，视图只绑定状态
- **Model 层**：数据模型，跨模块共享的下沉到服务层/基础层

### 理论基础参考

- Google 官方 Android Architecture（UI → Domain → Data 三层）
- Clean Architecture（Entities → Use Cases → Adapters → Frameworks）
- 国内大厂实践（壳工程 → 业务模块 → 中间件 → 基础库）
- Uber RIBs（跨平台共享业务逻辑）
- KMM（Shared Module + Platform Module）

我们的四层是国内大厂模型的提炼 + Clean Architecture 理论的融合。服务层的独立是实战对理论的补充。

### 服务端架构原则（参考对照）

服务端采用六边形（Ports & Adapters）：
- Domain 定义 Port（trait），适配器实现，依赖只能由外向内
- 客户端的四层分层与服务端的六边形在思想上一致：内层定义接口，外层实现
